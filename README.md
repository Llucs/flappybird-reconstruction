# Flappy Bird Reconstruction

An independent reconstruction of the historical Android version 1.3 of Flappy Bird, created for **study, preservation, and research**.

> This repository is a reconstruction based on APK analysis and decompilation. It is **not the original source code released by DotGears** and must not be presented as such.

The `original` branch is the main reconstruction branch. It contains the readable Java implementation of the application, the historical AndEngine dependency, the recovered resources used by the reconstruction, native libraries, and the legacy Android build configuration.

## Project status

The project aims to preserve the behavior and structure of the historical application as closely as possible. It is intentionally kept close to the original 2013-era Android environment rather than modernized for current Android development.

The main gameplay systems are present, including the launcher flow, bird physics, animation, pipe movement, collision detection, score handling, sound effects, buttons, transitions, and game-over handling.

This repository should be understood as a **historical reconstruction**, not as a production-ready Android application. The source, build system, third-party libraries, and service integrations are from an old Android ecosystem and may require a legacy environment to reproduce.

## Repository branches

| Branch | Purpose |
| --- | --- |
| `original` | Main branch. Contains the readable reconstruction of the application, project configuration, assets, native libraries, and the historical AndEngine dependency. |
| `AndEngine` | The historical AndEngine GLES2 library used by the application. This branch contains the engine, not the Flappy Bird application itself. |
| `jadx` | Java decompilation of the APK produced by JADX. It is preserved as a readable reference for analyzing the application logic. Decompiled names, types, and structure may differ from the original source. |
| `Apktool` | Low-level APK extraction containing Smali code, decoded resources, assets, and native libraries. It is preserved for bytecode and resource verification. |

The branches are complementary. `Apktool` preserves the closest low-level representation of the APK; `jadx` provides a more readable Java interpretation; `original` reorganizes and reconstructs that logic into maintainable Java source; and `AndEngine` provides the historical engine dependency used by the application.

## Reconstruction method

The readable reconstruction was produced by comparing the Java output generated by JADX with the Smali code and decoded resources generated by Apktool. The historical AndEngine implementation is preserved separately in the `AndEngine` branch and is included in the `original` branch as a local library module.

The `original` branch therefore represents a **readable, manually reconstructed implementation** intended to preserve the behavior and general structure of the historical application. It is not a literal recovery of the original DotGears source code. Decompiled code cannot reliably preserve the original names, comments, class organization, or all of the author’s intent.

The visual and audio resources, atlas description, and native AndEngine libraries are kept alongside the reconstruction so that they can be compared with the Apktool extraction.

## Historical build environment

The project uses the legacy Android Ant build system. It was designed for a historical toolchain rather than a current Gradle/Android Studio project.

The expected environment includes:

- Android SDK Tools r22.6.2 or a compatible historical SDK Tools installation;
- Android platform API 15;
- Android Platform Tools compatible with the historical SDK;
- compatible Android Build Tools;
- Apache Ant;
- a Java version compatible with the legacy Android build tools; and
- an Android device or emulator with OpenGL ES 2.0 support.

The exact toolchain may be difficult to reproduce on current operating systems. The repository includes `local.properties` files for the historical layout, but their SDK paths are machine-specific and must be changed before building on another computer.

After installing the required historical SDK, edit `local.properties` in the project root and set `sdk.dir` to the SDK location on your machine:

```properties
sdk.dir=/path/to/your/historical/android-sdk
```

Then run the legacy build from the root of the `original` branch:

```bash
ant debug
```

The `jadx`, `Apktool`, and `AndEngine` branches are reference/dependency branches and are not intended to be built as the final application independently. The `original` branch is the intended application project for reproducing the reconstruction.

## Historical integrations

The application retains historical integrations that were present in the analyzed APK, including legacy Google Play Games and advertising APIs. These integrations contain historical identifiers and are included for preservation of the reconstructed behavior, not as a recommendation for new applications.

A modern port should be implemented separately and should not modify the historical reconstruction unless the behavioral differences are explicitly documented. Updating Android APIs, replacing the game engine, or migrating Google services can change the runtime behavior and therefore belongs in a separate branch.

## Known limitations

Because the project is based on decompilation and reconstruction, some names and structures differ from the original application. A decompiler may also produce artifacts or references that are not used by the final runtime path. For example, legacy atlas references may remain even when a region is not used by the main scene.

The project does not include a modern Gradle build, automated test suite, or current Android service integrations. It should not be expected to compile with a current Android Studio installation without recreating or adapting the historical toolchain.

The native engine libraries are preserved for historical compatibility. Their presence does not imply support for every current Android device or ABI.
